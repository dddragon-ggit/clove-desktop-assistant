# 桌面操作助手产品规格文档

- 文档版本：`v0.3`
- 文档状态：`初稿`
- 创建日期：`2026-04-26`
- 适用阶段：`产品定义 / MVP 规划 / 后续研发启动`
- 当前假设：`Windows 优先`、`本地优先存储`、`云端模型优先`、`桌面悬浮助手形态`、`双 AI + 规则引擎 + 用户授权`

## 1. 文档目标

本文档用于统一这款桌面操作助手的产品边界、核心体验、安全机制、系统架构、数据结构与 MVP 范围，作为后续以下工作的依据：

- 产品原型设计
- 交互流程拆解
- 技术方案设计
- 数据模型设计
- 风险控制设计
- 开发任务拆分

本文档重点回答以下问题：

- 这个产品到底是什么，不是什么
- 用户与助手如何协作，谁做决定，谁做执行
- AI 在哪里参与，AI 的权限边界是什么
- 待办、提醒、桌面场景与电脑操作如何形成闭环
- 哪些动作能做，哪些动作绝对不能做
- 首个可交付版本应该做到什么程度

## 2. 产品概述

### 2.1 产品定位

本产品是一款 **桌面操作助手**，以悬浮桌面助手为主要入口，帮助用户：

- 记录并提醒待办事项
- 在合适的时机提醒用户处理任务
- 为任务展示建议操作与建议资源
- 在用户确认后执行安全范围内的电脑操作
- 以“桌面场景”的方式帮助用户更快进入某种工作或生活状态

它不是一个“万能自动代理”，也不是一个“全盘接管电脑”的 AI。  
它是一个 **有执行能力但受到严格控制的个人桌面助手**。

### 2.2 核心价值

本产品的核心价值不在于“替用户做尽可能多的事”，而在于：

- 降低重复操作成本
- 降低开始一项任务的心理和操作摩擦
- 把提醒、建议和执行衔接成一个顺滑的闭环
- 在安全边界内，帮助用户更自由地操控电脑
- 通过可理解、可确认、可撤销的方式建立长期信任

### 2.3 一句话描述

一句话定义：

> 一个悬浮在桌面上的个人助手，它会提醒你现在该做什么，并在你确认后，帮你安全地打开和组织完成这件事所需的软件、项目与资源。

## 3. 背景与问题定义

### 3.1 典型问题

在日常使用电脑时，用户常遇到以下问题：

- 知道自己有任务，但到点时没进入状态
- 想开始做某件事，但需要打开很多软件、网页、文件夹、项目目录，启动摩擦大
- 待办工具和实际工作环境是割裂的
- 提醒只会告诉你“该做了”，却不会帮你顺畅地开始
- 自动化工具虽然强，但配置复杂，且安全上难以信任
- 通用 AI 助手虽然会聊天，但不理解桌面场景，也不一定值得放权

### 3.2 机会点

本产品抓住的机会点是：

- 任务管理与桌面操作之间存在明显断层
- 用户真正需要的是“提醒 + 建议 + 确认执行”的组合，而不是完全自动化
- 桌面悬浮助手天然适合作为低打扰、高可见性的提醒入口
- 双 AI 审查 + 规则引擎 + 白名单可以大幅提升可信度

## 4. 产品边界

### 4.1 产品是什么

本产品是：

- 桌面操作助手
- 待办提醒助手
- 场景化工作流入口
- 安全可控的桌面动作执行器

### 4.2 产品不是什么

本产品不是：

- 全自动接管电脑的智能代理
- 可任意执行系统命令的脚本平台
- 管理员级系统优化工具
- 带有高度侵入性的监控软件
- 默认替用户决策的自动化机器人

### 4.3 首阶段明确不做

以下内容在首阶段不纳入产品范围：

- 任意 Shell / PowerShell 指令执行
- 删除文件
- 覆盖已有文件
- 修改注册表
- 修改系统关键设置
- 安装或卸载软件
- 自动输入密码或读取敏感凭据
- 自动发送消息、邮件或支付相关操作
- 鼠标键盘的任意接管式模拟

## 5. 设计原则

### 5.1 安全优先

任何执行能力都必须服从安全机制，安全边界高于智能程度。

### 5.2 提醒优先于替代

产品首先是提醒和组织助手，其次才是执行助手。

### 5.3 用户始终保留最终决定权

对于非零风险动作，系统只做建议与准备，不自动强行执行。

### 5.4 本地优先存储

用户的任务数据、场景数据、日志数据、授权数据应尽量保留在本地。

补充要求：

- 应用自身生成的数据文件默认落本地磁盘
- 应用自身生成的临时文件、缓存文件、导出文件不得写入 `C` 盘
- 首版建议提供可配置的数据根目录，例如 `D:/DesktopAssistantData`
- 数据根目录下建议拆分：
  - `data/`
  - `cache/`
  - `temp/`
  - `logs/`

说明：

- 本条默认理解为“应用主动创建的文件”不能落到 `C` 盘
- 对于运行时框架或系统自动产生的缓存，需在技术实现阶段继续评估是否也能完全迁移出 `C` 盘

### 5.5 低打扰

助手不应在用户专注、全屏、会议等场景下粗暴弹窗或自动打开软件。

### 5.6 可解释

每次执行前后，系统都应能够清楚说明：

- 要做什么
- 为什么这么做
- 风险是什么
- 做完了什么
- 哪些没成功

### 5.7 可追溯

所有执行动作都要有日志，用户能回看过去发生了什么。

### 5.8 可调试优先

系统的每条关键链路都应支持独立调试，而不是只能整条链路一起运行后再排查问题。

具体要求：

- 每个核心模块都应支持单独启动和调试
- 每个关键步骤都应有明确输入、输出和中间状态
- 复杂流程应支持 `dry-run` 与 `step-by-step` 运行
- 模块异常应尽量定位到单一模块，而不是在 UI 层统一报“失败”

### 5.9 模块解耦优先

系统应避免把 UI、AI、规则、执行、存储、联网上下文等能力写成彼此缠绕的单体逻辑。

具体要求：

- 模块间通过稳定接口通信
- 上层依赖抽象，不直接依赖某个具体实现
- AI 调用、规则判断、执行器、数据库、外部信息服务都应可替换
- 任一模块失效时，其他模块应尽量可单独运行或降级运行

## 6. 目标用户与使用场景

### 6.1 目标用户

首阶段目标用户为：**产品创建者本人**

这意味着：

- 可以优先服务个人真实使用习惯
- 可接受一定学习成本，但不可接受高风险
- 需要比通用工具更贴合个人桌面工作流

### 6.2 核心使用场景

#### 场景 A：到点提醒但不打断

- 用户正在处理其他事情
- 某项待办到达提醒时间
- 悬浮助手以颜色和简洁卡片提醒用户
- 不自动打开任务相关软件
- 用户稍后点击“开始处理”时才执行建议动作

#### 场景 B：一键进入任务状态

- 用户看到提醒“做周报”
- 助手展示建议打开：Notion、截图文件夹、本周项目目录
- 用户点击“开始处理”
- 系统完成安全范围内的资源打开与工作区准备

#### 场景 C：场景模式切换

- 用户主动唤起助手
- 选择“写作模式”或“收工模式”
- 助手展示将要执行的动作
- 用户确认后执行

#### 场景 D：快速记录待办

- 用户通过悬浮助手快速记录一条任务
- 可选绑定场景、提醒时间、建议资源
- 之后由悬浮助手在合适时刻提示

## 7. 核心产品结构

产品由以下核心模块组成：

1. 悬浮助手模块
2. 待办与提醒模块
3. 场景与工作区模块
4. 动作引擎模块
5. 双 AI 审查模块
6. 规则引擎模块
7. 用户授权与白名单模块
8. 日志与审计模块
9. 基础信息服务模块

## 8. 核心概念定义

### 8.1 任务（Task）

任务是用户希望在某个时间或某种情境下被提醒并处理的事项。

任务至少包含：

- 标题
- 描述（可选）
- 提醒时间
- 优先级
- 关联场景（可选）
- 建议动作列表
- 建议资源列表
- 状态

### 8.2 提醒（Reminder）

提醒是任务在某个时刻触发给用户的通知表现。提醒不等于执行。

### 8.3 场景（Scene）

场景是一组围绕某种目标状态的可复用工作流集合，例如：

- 写作模式
- 周报模式
- 复盘模式
- 收工模式

场景分为两类：

- 内置场景模板
- 用户自定义场景

用户应能够：

- 新建场景
- 修改场景
- 复制内置场景后再修改
- 启用或停用某个场景

AI 在场景系统中的职责不是“替用户完全决定场景内容”，而是：

- 将用户输入的自然语言场景描述整理成统一结构
- 补齐结构中缺失但必要的字段
- 将非结构化描述规范化为系统可执行的场景定义

场景通常包含：

- 推荐打开的软件
- 推荐打开的文件或文件夹
- 推荐打开的网页
- 展示的相关任务
- 可选的专注计时设置
- 场景元信息，如名称、颜色、图标、来源类型、版本

### 8.4 建议动作（Suggested Actions）

建议动作是系统基于任务、场景或历史行为，为用户展示的可执行操作集合。  
建议动作在用户确认前不能直接执行。

### 8.5 工作区快照（Workspace Snapshot）

工作区快照是某一次桌面状态的记录，用于恢复相似的工作环境。

### 8.6 白名单（Whitelist）

白名单是用户显式授权可重复执行的结构化动作集合。  
白名单不记录自然语言，不授权“任意能力”，而是授权具体动作模板。

### 8.7 基础信息（Context Signals）

基础信息是系统可用于提醒、建议与生成动作计划的环境信息。

来源包括：

- 本地系统信息
- 联网获取的信息

首版建议接入的基础信息类型：

- 当前时间
- 当前日期
- 星期
- 时区
- 节假日信息
- 天气信息

设计原则：

- 与提醒和场景判断强相关的信息优先接入
- 时间类信息默认优先读取本地系统时间
- 联网信息作为补充上下文，不应成为核心提醒能力的单点依赖

## 9. 产品体验总流程

### 9.1 从待办到执行的主链路

1. 用户创建任务
2. 用户可为任务绑定提醒时间、场景、建议资源
3. 到点后悬浮助手进行提醒
4. 用户看到任务卡片与建议动作
5. 用户选择：
   - 开始处理
   - 稍后提醒
   - 今天不处理
6. 若用户选择“开始处理”
7. 系统生成动作计划
8. 规则引擎审查
9. 审查 AI 审查
10. 若动作不在白名单，则展示确认卡片
11. 用户选择：
    - 拒绝
    - 本次运行
    - 加入白名单
12. 执行器逐步执行动作
13. 系统展示执行结果并写入日志

### 9.2 主链路原则

- 提醒与执行解耦
- AI 负责理解和规划，不直接拥有系统执行权
- 白名单只对结构化动作生效
- 危险动作永不进入白名单

## 10. 悬浮助手设计

### 10.1 产品形态

主形态为一个悬浮在桌面角落的助手卡片。它应满足：

- 常驻但低侵入
- 一眼可知当前状态
- 在需要时可展开任务内容
- 作为提醒与执行的统一入口

### 10.2 位置建议

初版建议默认右下角，支持用户后续手动调整位置。

### 10.3 状态定义

悬浮助手至少有以下状态：

#### 状态 S0：待机

显示内容：

- 当前时间
- 今日剩余任务数
- 当前模式或空闲状态

表现要求：

- 尺寸最小
- 颜色低饱和
- 不主动打断

#### 状态 S1：轻提醒

触发条件：

- 某任务即将在预设窗口内到点，例如 5 到 15 分钟内

显示内容：

- 即将开始的任务标题
- 距离开始时间

表现要求：

- 颜色轻度变化
- 不自动展开大卡片

#### 状态 S2：到点提醒

触发条件：

- 任务进入提醒时间

显示内容：

- 任务标题
- 任务摘要
- 建议动作
- 操作按钮

操作按钮：

- `开始处理`
- `稍后提醒`
- `今天不处理`

#### 状态 S3：高优先级未处理

触发条件：

- 高优先级任务到点后长时间未处理

表现要求：

- 更显著的颜色提醒
- 仍不自动打开任务软件
- 不以强制弹窗的形式干扰用户

#### 状态 S4：执行中

显示内容：

- 当前正在执行的动作
- 进度
- 当前步骤结果

#### 状态 S5：执行结果

显示内容：

- 已完成的动作列表
- 失败动作列表
- 日志入口

### 10.4 展开层级

悬浮助手建议具有两层交互：

- `缩略态`：仅展示状态与任务概览
- `展开态`：展示任务详情、建议动作、按钮、执行结果

### 10.5 打扰控制

以下情况下，悬浮助手应降低打扰等级：

- 当前为全屏应用
- 检测到会议类应用在前台
- 用户在短时间内持续高强度键鼠操作
- 用户已进入某种专注模式

此时策略为：

- 只变色或显示小红点
- 不自动展开任务卡片
- 不自动抢焦点

## 11. 待办与提醒系统设计

### 11.1 任务字段

每个任务建议包含以下字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | UUID | 是 | 唯一标识 |
| `title` | string | 是 | 任务标题 |
| `description` | string | 否 | 任务补充说明 |
| `status` | enum | 是 | `todo / in_progress / done / skipped / snoozed / archived` |
| `priority` | enum | 是 | `low / medium / high / critical` |
| `scheduled_at` | datetime | 否 | 计划处理时间 |
| `remind_at` | datetime | 否 | 首次提醒时间 |
| `scene_id` | UUID | 否 | 关联场景 |
| `resource_bundle_id` | UUID | 否 | 建议资源集 |
| `suggested_action_plan_id` | UUID | 否 | 建议动作计划 |
| `snooze_until` | datetime | 否 | 暂缓到何时 |
| `tags` | json | 否 | 标签 |
| `created_at` | datetime | 是 | 创建时间 |
| `updated_at` | datetime | 是 | 更新时间 |

### 11.2 提醒逻辑

提醒以“温和提醒 + 用户确认执行”为原则。

提醒层级建议：

- `预提醒`
  - 任务即将到点时轻提醒
- `准时提醒`
  - 到点时展示任务卡片
- `延期提醒`
  - 用户选择稍后提醒后，在新的时间点再次提醒
- `超时提醒`
  - 高优先级任务逾期时提高颜色等级

### 11.3 不自动执行原则

即使任务已经到点，也不应出现以下行为：

- 直接打开相关软件
- 直接切换用户窗口焦点
- 直接打开项目目录
- 直接恢复某个工作区

只有在用户点击 `开始处理` 或明确发出执行指令后，系统才进入动作审查与执行流程。

### 11.4 任务卡片交互

任务卡片中应展示：

- 任务标题
- 当前时间与提醒时间
- 关联场景
- 建议资源
- 建议动作
- 风险说明（如存在）

卡片按钮：

- `开始处理`
- `稍后提醒`
- `今天不处理`
- `查看更多`

### 11.5 稍后提醒策略

初版建议支持固定时间选项：

- 10 分钟后
- 30 分钟后
- 1 小时后
- 今天晚上
- 明天

后续可支持自定义时间。

## 12. 场景系统设计

### 12.1 场景目标

场景用于降低开始一类任务的操作摩擦。  
场景不是独立任务，而是任务的执行上下文与资源模板。

### 12.2 首批建议场景

首版建议支持以下内置场景模板：

- `写作模式`
- `周报模式`
- `学习模式`
- `收工模式`

同时，首版支持用户自行创建和修改场景。

首版建议规则：

- 内置场景模板可直接使用
- 内置场景模板可复制为自定义场景后再编辑
- 用户自定义场景优先级高于内置模板
- 所有场景最终都要落为统一的结构化定义

### 12.3 场景结构

一个场景可包含：

- 场景名称
- 场景说明
- 建议打开的应用列表
- 建议打开的网页列表
- 建议打开的文件夹列表
- 建议打开的文件列表
- 建议展示的任务过滤条件
- 专注时长设置（可选）
- 图标与颜色
- 来源类型：`builtin / custom`
- 结构化版本号
- 是否启用

建议的统一结构示意：

```json
{
  "id": "scene-weekly-review",
  "name": "周报模式",
  "description": "用于每周复盘与周报撰写",
  "source_type": "custom",
  "color": "orange",
  "enabled": true,
  "resources": {
    "apps": ["Notion"],
    "folders": ["D:/Work/Screenshots"],
    "files": ["D:/Templates/weekly-report.md"],
    "urls": ["https://example.com/dashboard"]
  },
  "task_filters": ["tag:weekly"],
  "focus_minutes": 40,
  "schema_version": "1.0"
}
```

### 12.3.1 用户自定义场景与 AI 规范化

用户可以用自然语言或表单方式描述场景，例如：

- “做周报的时候，帮我打开 Notion、截图文件夹和数据看板”
- “写作模式就是 Obsidian 加参考资料目录，再开一个 30 分钟专注”

系统处理流程：

1. 用户输入原始描述
2. AI 对描述进行结构化整理
3. 系统校验字段是否合法
4. 用户确认后保存为场景定义

AI 在该流程中的职责：

- 将模糊描述映射到合法字段
- 补全默认字段
- 识别无法解析的部分并要求用户确认
- 统一命名与字段格式

AI 不应做的事：

- 擅自为场景加入高风险动作
- 自动把不确定的资源写入正式场景
- 绕过用户确认直接保存

### 12.4 场景触发方式

场景可通过以下方式触发：

- 用户主动在悬浮助手中点击
- 任务到点后显示为建议场景

首版交互约束：

- 主要场景触发入口尽量收敛在悬浮助手内
- 不依赖全局快捷键作为首版核心入口

### 12.5 场景执行原则

场景本质上是一组动作集合，执行时需要：

- 经过规则引擎审查
- 经过审查 AI 审查
- 如未命中白名单，要求用户授权

### 12.6 首版工作区恢复范围

首版中，`restore_workspace` 的能力范围限定为：`只恢复资源打开状态`

具体含义：

- 可以重新打开相关应用
- 可以重新打开相关网页
- 可以重新打开相关文件夹
- 可以重新打开相关文件

首版明确不包含：

- 窗口布局恢复
- 多显示器位置恢复
- 标签页集合恢复
- 窗口尺寸和停靠位置恢复

这样设计的原因是：

- 优先保证执行稳定性
- 降低 Windows 桌面适配复杂度
- 先验证“提醒 -> 确认 -> 打开资源”主链路是否足够有价值

## 13. 动作系统设计

### 13.1 动作系统目标

动作系统用于定义“助手到底能做什么”。  
这是整个产品最核心的控制层之一。

### 13.2 动作设计原则

- 先少后多
- 先结构化后智能化
- 先安全后自由
- 先可预览后可执行

### 13.3 MVP 最小动作集合

首阶段动作集合建议如下：

| 动作类型 | 说明 | 示例 | 风险等级 | 可加入白名单 |
| --- | --- | --- | --- | --- |
| `open_app` | 打开应用 | 打开 Notion | 低 | 是 |
| `open_url` | 打开网页 | 打开日报页面 | 低 | 是 |
| `open_folder` | 打开文件夹 | 打开项目目录 | 低 | 是 |
| `open_file` | 打开文件 | 打开周报模板 | 中 | 是 |
| `show_tasks` | 展示筛选后的任务 | 展示今天的周报任务 | 低 | 是 |
| `restore_workspace` | 恢复工作区快照 | 恢复写作工作区 | 中 | 是 |
| `create_reminder` | 创建提醒 | 30 分钟后提醒 | 低 | 是 |
| `start_focus_timer` | 开始专注计时 | 开始 25 分钟计时 | 低 | 是 |

补充限制：

- `restore_workspace` 在首版中仅允许执行“打开相关资源”的动作集合
- 不允许包含窗口几何信息恢复
- 不允许包含多显示器布局恢复
- 不允许包含浏览器标签页编排恢复

### 13.4 暂不纳入 MVP 的动作

| 动作类型 | 原因 |
| --- | --- |
| `move_file` | 涉及数据位置变化，易产生误操作 |
| `rename_file` | 需要更复杂的回退机制 |
| `close_app` | 可能导致数据未保存 |
| `send_message` | 涉及对外行为与误发风险 |
| `run_shell` | 风险过高 |
| `delete_file` | 不可接受 |
| `modify_system_setting` | 超出首阶段能力边界 |

### 13.5 动作结构

每个动作应被标准化表示为结构化对象，例如：

```json
{
  "action_type": "open_app",
  "target": "Notion",
  "params": {
    "path": "C:/Users/xxx/AppData/Local/Programs/Notion/Notion.exe"
  },
  "risk_level": "low",
  "requires_user_confirmation": false,
  "whitelist_eligible": true
}
```

### 13.6 动作计划

多个动作可组合成动作计划（Action Plan）：

```json
{
  "plan_name": "weekly-report-setup",
  "source": "task_start",
  "steps": [
    {
      "action_type": "open_app",
      "target": "Notion"
    },
    {
      "action_type": "open_folder",
      "target": "D:/Work/Screenshots"
    },
    {
      "action_type": "open_url",
      "target": "https://example.com/dashboard"
    }
  ]
}
```

## 14. 风险分级与安全策略

### 14.1 风险等级定义

#### `Low`

特征：

- 不修改用户数据
- 不改变系统关键状态
- 不产生明显不可逆后果

示例：

- 打开应用
- 打开网页
- 创建提醒

#### `Medium`

特征：

- 可能影响当前工作流
- 可能引发误打开、误切换、误恢复
- 虽然可控，但需要更谨慎展示

示例：

- 打开文件
- 恢复工作区

#### `High`

特征：

- 涉及用户数据位置、状态变化
- 可能造成信息遗漏、数据损坏、上下文中断

示例：

- 关闭多个应用
- 移动文件
- 批量整理下载目录

#### `Critical`

特征：

- 具有明显不可逆或高损害风险
- 涉及系统设置、敏感信息或对外发送

示例：

- 删除文件
- 执行 shell 指令
- 改系统配置

### 14.2 风险处理矩阵

| 风险等级 | 规则引擎 | 审查 AI | 用户授权 | 白名单支持 | MVP 是否允许 |
| --- | --- | --- | --- | --- | --- |
| `Low` | 必须 | 必须 | 可按白名单决定 | 是 | 是 |
| `Medium` | 必须 | 必须 | 必须或命中白名单 | 是 | 是 |
| `High` | 必须 | 必须 | 必须 | 原则上否 | 否 |
| `Critical` | 直接拒绝 | 不进入 | 不允许 | 否 | 否 |

### 14.3 规则引擎优先级

规则引擎必须是最终硬边界，优先级高于 AI。

含义：

- 若规则引擎拒绝，动作不可进入下一步
- 审查 AI 只能否决，不能突破规则引擎
- 白名单也不能覆盖规则引擎的禁令

## 15. 双 AI 审查系统设计

### 15.1 设计目标

通过两层 AI 参与机制，提高“理解用户意图”和“发现风险”的能力，但不让 AI 获得无限执行权。

### 15.2 角色划分

#### AI-1：规划助手（Planner AI）

职责：

- 理解用户自然语言输入
- 将任务、场景或命令翻译成结构化动作计划
- 解释动作为何被建议

禁止：

- 直接执行系统命令
- 生成任意脚本并交由系统运行

#### AI-2：审查助手（Reviewer AI）

职责：

- 审查 AI-1 生成的动作计划是否偏离用户意图
- 判断动作是否可能带来风险
- 给出风险分析与审核意见

输出内容应包含：

- 是否通过
- 风险等级
- 风险原因
- 是否建议要求用户二次确认

禁止：

- 单独发放新权限
- 绕过规则引擎

### 15.3 推荐执行链路

```text
用户输入 / 任务触发
  -> AI-1 生成动作计划
  -> 规则引擎进行硬规则校验
  -> AI-2 进行意图与风险审查
  -> 查询白名单
  -> 用户确认
  -> 执行器执行
  -> 日志记录
```

### 15.3.1 可调试链路要求

上述链路中的每一步都应支持独立观察与调试。

最少要求包括：

- 能单独查看 AI-1 输入与输出
- 能单独查看规则引擎输入与输出
- 能单独查看 AI-2 输入与输出
- 能单独查看白名单命中结果
- 能单独查看执行器收到的最终动作计划

建议为每次链路执行分配统一的 `trace_id`，贯穿：

- UI 触发
- 任务调度
- AI 规划
- 规则判断
- 审查判断
- 用户授权
- 执行动作
- 日志写入

### 15.4 AI 输出格式要求

无论使用何种模型，AI 都必须输出结构化数据，禁止输出自由系统命令。

建议输出字段：

- `intent_summary`
- `action_plan`
- `risk_guess`
- `reasoning_summary`

### 15.5 提示词设计原则

由于本产品包含多个 AI 参与环节，提示词必须被视为正式系统资产，而不是临时文案。

提示词设计原则：

- 明确角色边界
- 明确输入上下文
- 明确禁止事项
- 明确输出格式
- 明确异常处理方式
- 明确不确定时如何降级

所有提示词都应遵守以下底线：

- 不生成自由系统命令
- 不生成未注册动作类型
- 不假设不存在的本地资源一定存在
- 不将用户未明确授权的内容写入白名单
- 遇到歧义时输出“需要确认”的结构化标记

### 15.6 提示词上下文输入规范

传给 AI 的上下文建议拆成以下部分：

- `user_request`
- `current_time_context`
- `task_context`
- `scene_context`
- `allowed_actions`
- `risk_policy`
- `whitelist_summary`
- `system_capabilities`
- `external_context`
- `model_provider_context`

其中：

- `current_time_context` 可包含当前时间、日期、星期、时区
- `external_context` 可包含天气、节假日等联网信息
- `allowed_actions` 必须始终随请求一起发送，避免模型幻想能力
- `model_provider_context` 可包含当前启用的模型提供方名称、基地址标识与能力标签，但不直接下发明文密钥

### 15.7 AI-1 规划助手提示词模板

建议为 AI-1 准备稳定的系统提示词。示例：

```text
你是一个 Windows 桌面操作助手中的“规划助手”。
你的任务是把用户需求翻译为结构化动作计划。

你必须遵守以下规则：
1. 你只能使用系统提供的 allowed_actions。
2. 你不能生成 shell、PowerShell、cmd、脚本或任何自由命令。
3. 你不能假设未知文件路径真实存在。
4. 如果用户意图不清晰，你必须在输出中标记 requires_clarification=true。
5. 你不能创建高风险或被禁止的动作。
6. 你输出的所有内容必须是结构化 JSON，不要输出额外解释文字。

你的目标：
- 准确理解用户意图
- 给出最小且合理的动作计划
- 对每个动作给出简短理由
- 标记可能的风险与不确定性
```

AI-1 请求模板建议：

```json
{
  "user_request": "开始做周报",
  "current_time_context": {
    "local_time": "2026-04-26T19:00:00+08:00",
    "weekday": "Sunday"
  },
  "task_context": {
    "task_title": "做周报",
    "scene_name": "周报模式"
  },
  "allowed_actions": [
    "open_app",
    "open_url",
    "open_folder",
    "open_file",
    "show_tasks",
    "restore_workspace",
    "create_reminder",
    "start_focus_timer"
  ],
  "risk_policy": {
    "forbidden_actions": ["run_shell", "delete_file", "modify_system_setting"]
  }
}
```

AI-1 输出模板建议：

```json
{
  "intent_summary": "用户希望开始处理周报相关任务",
  "requires_clarification": false,
  "action_plan": [
    {
      "action_type": "open_app",
      "target": "Notion",
      "reason": "周报通常在 Notion 中整理"
    },
    {
      "action_type": "open_folder",
      "target": "D:/Work/Screenshots",
      "reason": "周报需要引用本周截图素材"
    }
  ],
  "risk_guess": "medium",
  "reasoning_summary": "动作均为允许动作，未包含高风险系统操作"
}
```

### 15.8 AI-2 审查助手提示词模板

建议为 AI-2 准备独立系统提示词。示例：

```text
你是一个 Windows 桌面操作助手中的“审查助手”。
你的任务不是帮助执行，而是判断规划动作是否安全、是否偏离用户意图、是否需要用户确认。

你必须遵守以下规则：
1. 你不能新增动作，只能审查已有动作计划。
2. 你不能降低规则引擎已经判定的风险等级。
3. 你不能授予新权限。
4. 如果动作存在明显意图偏差、资源不确定或潜在风险，你应拒绝通过。
5. 你输出的所有内容必须是结构化 JSON。

你需要重点检查：
- 动作是否超出用户请求
- 是否存在不可逆风险
- 是否涉及敏感路径或高风险能力
- 是否需要用户额外确认
```

AI-2 输出模板建议：

```json
{
  "approved": true,
  "risk_level": "medium",
  "review_summary": "动作与周报场景匹配，未发现禁止动作",
  "needs_user_confirmation": true,
  "issues": [],
  "rejection_reason": null
}
```

### 15.9 场景规范化提示词模板

当用户创建或修改场景时，建议使用专门的“场景规范化”提示词，而不是直接复用执行提示词。

示例：

```text
你负责把用户描述的桌面场景整理为统一格式。
你只能输出合法的场景结构，不能输出任何执行命令。

请遵守：
1. 只使用系统允许的资源字段：apps、folders、files、urls、task_filters、focus_minutes。
2. 遇到不确定资源时，保留 unresolved_items。
3. 不要擅自加入高风险动作。
4. 名称、描述、颜色、资源字段都应保持简洁。
5. 输出 JSON，不要输出解释。
```

建议输出：

```json
{
  "scene_name": "写作模式",
  "description": "写作时使用的基础资源集合",
  "resources": {
    "apps": ["Obsidian"],
    "folders": ["D:/Notes/References"],
    "files": [],
    "urls": []
  },
  "task_filters": ["tag:writing"],
  "focus_minutes": 30,
  "unresolved_items": []
}
```

### 15.10 提示词版本管理

提示词需要纳入版本管理。

建议：

- 为 AI-1、AI-2、场景规范化分别维护独立提示词文件
- 为每份提示词记录版本号与更新时间
- 关键修改应有变更说明
- 每次修改提示词后，使用固定测试样例回归验证

建议测试样例至少覆盖：

- 正常的低风险任务
- 含歧义的任务
- 明显越权的请求
- 自定义场景创建
- 白名单命中场景
- 审查 AI 应拒绝的场景

## 16. 用户授权系统设计

### 16.1 用户授权选项

当动作计划未命中白名单时，用户可选择：

- `拒绝`
- `本次运行`
- `加入白名单`

### 16.2 选项解释

#### `拒绝`

- 当前动作不执行
- 记录一次拒绝日志

#### `本次运行`

- 仅本次执行
- 不形成长期授权

#### `加入白名单`

- 将当前结构化动作模板记录到白名单
- 以后命中该白名单时，可在满足规则引擎和审查 AI 通过的前提下直接执行

### 16.3 白名单设计原则

- 白名单记录的是结构化动作，不是自然语言
- 白名单必须可查看、可关闭、可删除
- 白名单不应允许覆盖高风险禁令
- 白名单应支持过期时间或后续撤销

### 16.4 白名单项建议结构

| 字段 | 说明 |
| --- | --- |
| `id` | 唯一标识 |
| `action_fingerprint` | 动作指纹 |
| `action_type` | 动作类型 |
| `target` | 目标 |
| `scope` | 作用范围 |
| `risk_level` | 风险等级 |
| `created_at` | 创建时间 |
| `last_used_at` | 上次使用时间 |
| `expires_at` | 过期时间，可空 |
| `enabled` | 是否启用 |

### 16.5 动作指纹建议

动作指纹应根据以下字段稳定生成：

- 动作类型
- 目标标识
- 关键参数
- 风险等级

例如：

```text
open_app|Notion|default|low
restore_workspace|writing_mode|workspace:default|medium
```

## 17. 规则引擎设计

### 17.1 职责

规则引擎是产品的核心安全边界，负责：

- 校验动作类型是否在允许范围内
- 校验目标资源是否在可接受范围内
- 判断动作风险等级
- 阻止禁用动作流入执行层

### 17.2 初版规则建议

初版规则至少包括：

- 仅允许执行注册过的动作类型
- 禁止所有 `Critical` 动作
- 禁止执行任何任意命令字符串
- 禁止访问系统敏感目录的写操作
- 禁止管理员提权
- 禁止自动发送外部请求型动作

### 17.3 规则执行顺序

1. 校验动作类型是否合法
2. 校验参数是否合法
3. 判断风险等级
4. 校验是否允许进入白名单逻辑
5. 输出决策结果

## 18. 执行器设计

### 18.1 执行器职责

执行器负责在授权完成后，逐步执行结构化动作计划。

### 18.2 执行器原则

- 严格按动作计划执行
- 不补充额外动作
- 每步执行都要记录状态
- 出错时立即停止或按策略继续

### 18.3 执行结果状态

每个动作执行后应返回：

- `success`
- `failed`
- `skipped`
- `cancelled`

### 18.4 执行可见性

执行过程中，悬浮助手应显示：

- 当前动作
- 执行进度
- 已完成数量
- 失败数量

### 18.5 执行模式

为保证工程可调试、可逐步构建，执行器至少应支持以下运行模式：

#### `normal`

- 正常执行所有已通过审查与授权的动作

#### `dry_run`

- 不真正操作系统
- 只生成并展示即将执行的动作清单
- 用于验证规划、规则、审查与白名单逻辑是否正确

#### `step_by_step`

- 每次只执行一个动作
- 执行前展示当前步骤信息
- 用户或开发者确认后进入下一步
- 适合调试复杂场景与排查问题

#### `module_test`

- 不走完整产品链路
- 仅测试某个模块，例如：
  - 只测 AI-1 规划
  - 只测规则引擎
  - 只测 AI-2 审查
  - 只测执行器

### 18.6 单步执行要求

单步执行模式下，每一步应展示：

- 当前步骤序号
- 动作类型
- 目标资源
- 风险等级
- 是否命中白名单
- 上一步执行结果

用户或开发者可选择：

- 执行下一步
- 跳过本步
- 终止本次流程

### 18.7 模拟执行与假适配器

为了保证系统能够逐步构建完成，执行层应支持“模拟适配器”。

模拟适配器的作用：

- 不真正打开应用或文件
- 只返回“假成功”或“假失败”
- 让 UI、AI、规则、日志等上层逻辑先跑通

首版建议至少为以下模块提供模拟实现：

- AI-1 规划器
- AI-2 审查器
- 执行器
- 联网基础信息服务

## 19. 日志与审计设计

### 19.1 日志目标

日志用于提升系统透明度和可追溯性。

### 19.2 日志记录内容

每次动作执行应记录：

- 触发来源
- 原始输入
- 动作计划
- 规则引擎判断结果
- 审查 AI 判断结果
- 用户授权方式
- 实际执行结果
- 时间戳

### 19.3 日志使用场景

- 用户回看助手做过什么
- 调试错误执行
- 排查误操作
- 优化白名单策略

## 20. 异常处理与降级策略

### 20.1 模型不可用

当 AI 模型不可用时：

- 基础提醒功能仍可正常工作
- 规则式任务建议仍可工作
- 复杂自然语言理解功能降级
- 用户可手动启动场景

### 20.2 审查 AI 未通过

若审查 AI 不通过：

- 不执行动作
- 告知用户原因
- 可允许用户查看被拒绝的动作计划

### 20.3 执行器失败

例如：

- 应用不存在
- 文件路径失效
- 工作区快照找不到

系统应：

- 告知失败原因
- 标记哪些动作已完成、哪些未完成
- 提供重新尝试入口

### 20.4 用户中途取消

若用户取消执行：

- 终止剩余动作
- 记录取消日志
- 已执行动作不回滚，除非未来支持明确撤销能力

## 21. UI 模块设计建议

### 21.1 MVP 所需页面/面板

初版建议包含以下主要界面：

1. 悬浮助手主卡片
2. 任务列表面板
3. 新建/编辑任务面板
4. 场景列表与编辑面板
5. 授权确认面板
6. 白名单管理面板
7. 操作日志面板

补充要求：

- 首版主要交互尽量都在悬浮助手内部完成
- 任务创建、任务提醒、场景编辑、授权确认、日志入口都应从悬浮助手展开
- 除非是系统级设置或首次配置，不优先依赖独立大窗口

### 21.2 悬浮助手主卡片

核心内容：

- 当前状态
- 即将开始或当前提醒任务
- 快捷操作按钮
- 快速记录入口

### 21.3 新建任务面板

建议字段：

- 标题
- 时间
- 优先级
- 关联场景
- 推荐资源
- 是否允许生成建议动作

### 21.4 授权确认面板

应展示：

- 此次操作摘要
- 动作列表
- 风险等级
- 审查 AI 意见
- 当前是否命中白名单
- 操作按钮：`拒绝 / 本次运行 / 加入白名单`

### 21.5 首次模型接入配置面板

由于首版采用云端模型优先，应用首次可用前需要完成模型接入配置。

- 输入 `Base URL`
- 可选输入模型名称或默认模型映射

- 替换 `Base URL`
- 测试新配置

安全要求：

- `API Key` 默认遮罩显示
- 不在普通日志中打印明文 `API Key`
- 配置变更后应更新连接状态

## 22. 技术架构建议

### 22.1 技术目标

技术实现需要满足：

- 桌面常驻
- 本地存储
- 系统托盘能力
- 桌面悬浮窗口
- 调用本地系统能力
- 可接入一个或多个 LLM
- 可接入联网基础信息服务
- 可配置非 `C` 盘数据目录
- 支持云端模型接入配置与热更新

补充说明：

- 全局快捷键可作为后续增强能力，不作为首版核心依赖

### 22.2 推荐技术栈

首版建议：

- 主语言：`Python`
- 桌面框架：`PySide6`
- UI 组织方式：`Qt Widgets` 或 `Qt Quick`，首版更建议 `Qt Widgets`
- 本地数据库：`SQLite`
- 数据建模与校验：`Pydantic`
- 网络请求：`httpx`
- 本地存储访问：`sqlite3` 或轻量数据库封装
- Windows 系统适配层：`pywin32 + subprocess + 可控 Win32 能力封装`

补充说明：

- 之所以采用 `Python`，是因为项目创建者需要能够自行阅读、检查和维护代码
- 首版优先选择可读性与可调试性，而不是追求极限性能

### 22.3 分层架构

#### 表现层（Renderer）

负责：

- 悬浮助手 UI
- 任务与场景面板
- 授权确认面板
- 日志展示

#### 应用层（App Service）

负责：

- 任务管理
- 提醒调度
- 场景管理
- 白名单管理
- 日志管理
- 模型接入配置管理

#### 智能层（AI Service）

负责：

- AI-1 规划
- AI-2 审查
- 场景规范化
- 输出结构化计划
- 读取当前生效的模型接入配置

#### 信息层（Context / Info Service）

负责：

- 读取本地时间、日期、时区
- 获取联网基础信息
- 统一向 AI 与提醒模块提供上下文

首版建议支持的基础信息：

- 本地时间
- 日期与星期
- 时区
- 节假日
- 天气

#### 配置层（Config / Provider Service）

负责：

- 保存模型接入配置
- 读取当前生效的 `API Key` 与 `Base URL`
- 测试云端模型连通性
- 支持运行中替换配置并刷新连接状态
- 向 AI Service 提供已脱敏的提供方信息

#### 安全层（Policy / Rules）

负责：

- 动作校验
- 风险分级
- 白名单匹配

#### 执行层（Execution）

负责：

- 打开应用、文件、文件夹、网页
- 工作区恢复
- 专注计时

### 22.3.1 模块解耦原则

为避免形成难以维护的大型耦合逻辑，建议采用“接口 + 编排器 + 适配器”模式。

推荐原则：

- UI 不直接调用 AI SDK、数据库或系统命令
- AI Service 不直接操作数据库或系统执行器
- 规则引擎不依赖 UI 和具体模型实现
- 执行器不依赖 AI 内部逻辑，只接收结构化动作计划
- 外部服务都通过适配器封装接入

推荐依赖方向：

```text
UI
 -> Application Orchestrator
   -> Planner Interface
   -> Reviewer Interface
   -> Policy Interface
   -> Executor Interface
   -> Context Provider Interface
   -> Storage Interface
```

### 22.3.2 建议拆分的核心模块

首版建议将系统拆为以下可独立调试模块：

1. `ui_shell`
   - 悬浮助手与面板展示
2. `task_service`
   - 任务与提醒逻辑
3. `scene_service`
   - 场景创建、编辑、规范化保存
4. `planner_service`
   - AI-1 规划
5. `reviewer_service`
   - AI-2 审查
6. `policy_engine`
   - 风险分级与白名单判断
7. `execution_engine`
   - 结构化动作执行
8. `provider_config_service`
   - `API Key / Base URL` 管理
9. `context_service`
   - 时间、天气、节假日等上下文
10. `log_service`
   - trace、执行日志、错误日志

每个模块至少应满足：

- 有清晰职责
- 有清晰输入输出
- 可被模拟实现替换
- 可独立单测或局部调试

### 22.3.3 编排器职责

建议增加单独的 `Application Orchestrator` 或 `Workflow Orchestrator`。

它负责：

- 把多个模块串成完整业务链路
- 生成统一的 `trace_id`
- 维护当前执行状态
- 协调 `dry_run`、`step_by_step` 和 `normal` 模式

它不负责：

- 直接写 UI
- 直接调用系统命令
- 直接包含模型提示词细节

### 22.3.4 模块测试替身

为便于逐步开发，建议每个关键接口都允许注入替身实现：

- `FakePlanner`
- `FakeReviewer`
- `FakeExecutor`
- `FakeContextProvider`
- `InMemoryStorage`

这样在某个真实模块尚未完成时，其他模块仍可先开发和调试。

### 22.4 数据目录与临时文件策略

首版建议引入统一数据根目录，例如：

```text
D:/DesktopAssistantData/
  data/
  cache/
  temp/
  logs/
```

目录约定：

- `data/`：SQLite 数据库、用户配置、场景定义
- `cache/`：联网基础信息缓存、AI 响应缓存
- `temp/`：应用生成的临时文件
- `logs/`：结构化日志与调试日志

关键要求：

- 应用主动创建的临时文件不写入 `C` 盘
- 导出文件、下载文件、缓存文件默认也不写入 `C` 盘
- 首次启动时应允许用户确认数据根目录

补充要求：

- 若使用本地配置文件保存模型接入信息，其存储位置也应位于非 `C` 盘数据目录下
- `API Key` 不应以明文写入普通日志

### 22.5 提示词资产组织建议

提示词建议作为独立资产管理，而不是写死在零散代码中。

建议目录结构：

```text
src/prompts/
  planner/
    system.md
    tests.json
  reviewer/
    system.md
    tests.json
  scene-normalizer/
    system.md
    tests.json
```

每类提示词建议包含：

- 系统提示词
- 输入模板说明
- 输出 JSON Schema
- 回归测试样例

### 22.6 Python 应用运行结构建议

Python 版首版建议拆分为：

- `UI Runtime`
  - 悬浮助手窗口
  - 面板与交互
  - 托盘入口
- `Application Core`
  - 工作流编排器
  - 任务与场景服务
  - 规则引擎
  - 调试运行控制
- `Adapters`
  - AI 提供方适配器
  - Windows 执行适配器
  - 联网上下文适配器
  - 存储适配器

说明：

- 首版不强依赖多进程
- 优先保持单进程、模块化、可调试
- 如后续发现 UI 卡顿或隔离需求明显，再考虑把 AI 调用或执行层拆到后台 worker

### 22.7 当前工程结构约定

当前实现采用“根目录保留入口与稳定门面，具体能力进入子包”的结构。根目录不再作为实现文件堆放区；新增功能应优先放入对应领域目录，只有需要对外保持稳定导入路径时才在根目录增加薄门面。

```text
desktop_assistant/
  __main__.py                 # 包运行入口
  __init__.py                 # 包标识
  action_trust.py             # 动作级信任、确认与白名单规则
  config.py                   # provider 配置读取与校验
  demo.py                     # 组装 planner/reviewer/policy/executor 的启动入口
  models.py                   # 全局工作流、动作、风险、执行结果模型
  protocols.py                # Planner/Reviewer/Executor 等抽象接口
  capabilities.py             # capability 公开门面
  capability_store.py         # capability store 兼容门面
  capability_executor.py      # capability executor 兼容门面
  project_locator.py          # project 公开门面
  prompt_templates.py         # prompting 公开门面
  recipes.py                  # recipe 公开门面
  capability/                 # 能力目录、风险校验、handler 分发与持久化
  projects/                   # 项目/文件夹目录、发现、匹配与持久化
  prompting/                  # 可复用提示词加载、渲染、应用清单摘要
  prompts/                    # 提示词文本与 JSON 模板资产
  recipe/                     # 可复用方案/配方的模型、检查、细化与存储
  activity/                   # 用户当前应用/文件/项目活动的元数据感知与记录
  todo/                       # 真实待办、提醒时间、重要事项和紧急度计算
  habits/                     # 用户行为日记、14 天保留策略、下一步行为预测
  workspace/                  # 任务/目标到工作区建议与可执行动作计划
  input_router/               # 初始输入框意图路由与预测接受处理
  ui_state/                   # 助手方框/小球位置、尺寸、透明度、隐身状态持久化
  confirmation/               # 前端可直接消费的动作级确认流 API
  core/                       # 编排、策略、失败恢复闭环
  adapters/                   # OpenAI、fake、Windows、本地应用、窗口、网页查询适配器
  storage/                    # SQLite 与内存存储实现
  tools/                      # smoke/quality/execution/capability 调试工具
  ui/                         # PySide6 UI、面板、view model、worker
```

职责边界：

- `models.py` 只放跨模块共享的数据结构；领域私有模型放入各自子包的 `models.py`。
- `capability/` 是动作能力的单一来源，负责 capability 默认定义、风险/目标校验、handler 可用性、执行分发和能力目录 JSON。
- `projects/` 只处理本地项目与常用文件夹定位，不承担真实打开动作；真实执行仍由 Windows adapter 完成。
- `prompting/` 只负责提示词模板选择、填词和上下文摘要；具体模型请求留在 `adapters/openai_*`。
- `recipe/` 只负责“用户目标 -> 可保存方案 -> 细化 -> 检查 -> 复用”的产品化配方能力。
- `activity/` 只读取桌面外层元数据，用于判断当前应用、可能打开的文件、所属项目和最近活动；禁止记录键盘输入、截图、OCR、文档正文、聊天内容或网页正文。
- `todo/` 负责真实待办增删改查、完成/推迟、提醒时间与首页状态颜色，不再使用 fake task 作为 UI 数据源。
- `habits/` 负责应用运行期间的活动采样落盘、每日行为摘要、14 天过期清理和下一步行为预测文件维护。
- `workspace/` 负责把待办或用户目标转成可确认的工作区建议；建议执行仍必须经过 policy/reviewer/action-level trust。
- `input_router/` 负责首页输入框的轻量路由：待办、工作区、继续刚才工作或进入对话页。
- `ui_state/` 只保存助手外壳状态，不包含业务逻辑：方框/小球位置、大小、透明度、模糊、隐身化。
- `confirmation/` 对 policy/action trust 做前端友好的封装，输出每个 action 的风险、原因和拒绝/本次/永久确认选项。
- `core/` 只编排工作流和安全策略，不直接依赖 UI 组件，也不直接写具体 Windows 操作。
- `adapters/` 是外部世界边界。Windows、OpenAI、网页查询、fake 后端都在这里隔离，便于替换和测试。
- `ui/` 只负责展示、交互和把用户选择转成工作流请求；业务规则应下沉到 `core/`、领域子包或 adapter。

### 22.8 活动感知模块约定

`activity/` 模块用于回答“用户当前大概在使用什么应用、打开了什么文件、处于哪个项目”这一层问题，为后续前端状态栏、最近活动、继续刚才项目、基于上下文生成方案等能力提供基础。

能力范围：

- 读取前台窗口标题、进程 ID、可执行文件路径等窗口/进程元数据。
- 结合 `app_inventory.json` 识别应用名称。
- 结合进程命令行、窗口标题和 Windows Recent Items 推断当前文件名或文件路径。
- 结合 `projects.json` 通过文件路径或窗口标题推断所属项目。
- 将活动快照持久化到 `runtime/data/activity_log.json`，并对连续相同活动做合并更新。
- 支持隐私设置：暂停记录、清空记录、排除指定应用、仅保存文件名不保存完整路径。

隐私边界：

- 不监听键盘。
- 不读取剪贴板。
- 不截图，不 OCR。
- 不读取文件正文。
- 不读取网页正文或聊天内容。
- 只保存应用、窗口、文件名/路径、项目名/路径等元数据。

当前实现文件：

- `activity/models.py`：`ActivitySnapshot`、`ActivityApp`、`ActivityFile`、`ActivityProject` 等结构。
- `activity/resolver.py`：把窗口、命令行、最近文件、项目目录归因为活动快照。
- `activity/sampler.py`：采样当前前台窗口并组装 resolver。
- `activity/recent_files.py`：读取 Windows Recent Items 快捷方式元数据。
- `activity/process.py`：通过 WMI 读取进程命令行元数据。
- `activity/store.py`：本地活动快照 JSON 持久化。

### 22.9 首页助手 UI 的后端契约

首页形态：

- 默认在屏幕右上角显示一个小型水雾/朦胧背景方框，约占屏幕面积 `1/8` 到 `1/12`。
- 方框可拖动、可调整大小；每个页面状态都必须有最小化入口。
- 最小化后变成可拖动小球，并支持隐身化。
- 小球不应只是静态图标；首版实现为 `LivingOrb`，主视觉固定为橙色绒毛小球。小球采用简单 2D 毛绒形态，不显示嘴巴，不显示外圈虚框，仅保留 E 款安静小圆眼、短绒毛边缘、柔和毛面纹理、轻微呼吸、眨眼、空闲视线游移和靠近鼠标时的视线追踪。小球模式必须使用圆形窗口遮罩，并通过 `ui/native_window.py` 调用 Windows DWM 原生接口关闭非客户区渲染、窗口圆角和边框颜色，避免透明顶层窗口残留类似选中标记的圆角方框。
- 方框状态显示问候语：早上好、下午好、晚上好。
- 方框第二行显示重要待办数量。
- 背景色由最近提醒任务决定：30 分钟内红色，3 小时内橙色，大于 3 小时或无时间黄色，全部完成绿色。
- 当前 PySide 首屏由 `ui/shell_window.py` 提供，启动入口默认打开新版小型 Shell；旧的调试型 `FloatingAssistantWindow` 保留为工程调试资产，不作为日常默认入口。
- Shell 视觉基调为半透明水雾感卡片、白色文字、柔和阴影和状态色背景；窗口位置、尺寸、小球状态继续由 `ui_state/` 持久化。
- 方框模式和小球模式的窗口属性必须分离：小球模式可以启用透明/无背景属性来消除原生方框痕迹；回到方框模式时顶层窗口仍需保持 `WA_NoSystemBackground=True`，根容器保持 `WA_TranslucentBackground=True` 但关闭根容器 `WA_NoSystemBackground`，这样圆角外侧透明、水雾背景仍正常绘制。
- 拖动能力应覆盖页面空白、标题和普通文字区域；按钮、输入框、列表、文本框和缩放角保持原交互，不作为拖动触发区域。
- 小球视觉以固定 `180x180` 设计稿坐标绘制，再缩放到实际窗口尺寸，避免 `78x78` 程序小球和放大预览出现比例、绒毛和眼睛差异；启动时不应立即眨眼，以免首次展示变成半眯眼状态。

第二页面入口：

- 鼠标悬停或点击首页方框进入第二页面。
- 第二页面居中显示三个圆角按钮：
  - 待办任务清单。
  - 工作环境选择。
  - 继续刚才的工作。
- 三个入口按钮必须在最小面板尺寸下保持清晰间距，不得互相重叠或压住底部输入框。
- 底部输入框可以输入任意内容；后端根据 `input_router/` 判断走待办、工作环境、继续工作或对话页。
- 输入框可展示灰色预测文本；用户按 `Tab` 接受预测，文本变黑；再按 `Enter` 发送。
- 如果用户只输入“继续 / 恢复 / 刚才 / 上次”等模糊词，`input_router/` 应优先使用当前预测补全成具体目标，而不是把原始短词直接交给后续流程。
- 首版 UI 中，待办入口支持查看、新增、完成、删除和从待办生成工作区建议；工作环境入口支持生成建议、按用户反馈调整、保存草稿和进入规划；对话与规划页复用现有 dry-run / run-once 链路。

待办任务清单：

- 后端必须提供真实 To-do CRUD，而不是 fake 展示。
- 待办支持无时间和有时间两种形态。
- 待办支持重要性、完成状态、是否需要电脑完成。
- 进入某个需要电脑完成的待办后，`workspace/` 生成工作区建议，包括应用、网页、文件、项目。
- 用户可补充意见，后端重新生成建议；用户确认后交给现有 orchestrator 执行。

工作环境选择：

- 用户输入目标，后端生成工作区建议。
- 用户补充要求后可重新生成。
- 用户确认后执行并可保存为 recipe。
- 所有涉及打开应用、网页、文件、项目、窗口管理的动作都必须继续走 policy/reviewer/action-level trust。
- 中风险及以上动作展示拒绝、本次确认、永久确认。

行为记录与预测：

- 应用启动期间，`habits/` 基于 `activity/` 定时捕获活动快照。
- 每天生成一个按日期命名的简单行为记录文档，例如 `runtime/data/activity_days/2026-04-30.md`。
- 只保留最近 14 天记录，过期自动删除。
- 维护随时变化的 `runtime/data/next_action_prediction.json`，供首页输入框展示预测。
- 预测内容必须可解释，包含推荐文本、来源、置信度和可选动作目标。
- 预测不得只是复述当前 app 状态；如果没有待办、未完成流程、项目、文件或习惯时间信号，兜底应回到待办清单，而不是提示“继续使用 Cursor”。
- 预测策略优先级：
  - 紧急待办：临近任务优先提示处理或准备工作区。
  - 未完成流程：上次生成但未确认/未执行的工作区建议优先恢复。
  - 恢复中断：当前活动与最近有意义活动不一致时，按时间戳选择最近的项目/文件上下文提示恢复，避免回到过旧记录。
  - 习惯时间：根据最近 14 天同一时间段的重复应用/项目行为给出建议。
  - 上下文补全：用户输入“继续”时，把当前项目/文件补成具体目标，例如“继续 desktop_assistant 的 UI 设计”。
  - 兜底：查看待办清单，而不是机械复述当前 app。

本轮后端完成标准：

- `show_tasks` 和 `create_reminder` 必须接入真实 `todo/`，不再依赖 simulated handler。
- `todo/` 必须支持推迟、取消、上次执行记录、工作区确认状态。
- `habits/` 必须提供非 UI 的定时采样 worker/service。
- `activity/` 必须提供隐私配置和清空记录能力。
- `workspace/` 必须支持用户反馈 refine，并能保存为 recipe。
- `confirmation/` 必须提供前端可直接渲染的动作级确认摘要与永久信任写入。
- `ui_state/` 必须能持久化方框/小球显示状态。

前端暂未直接使用但应预留的后端能力：

- `capability/`：能力目录和 handler 可用性，可作为调试/设置页。
- `projects/`：项目发现与人工修正，可作为工作环境选择的数据源。
- `recipe/`：保存确认后的工作区方案，形成可复用场景。
- `activity/`：当前活动与最近上下文，可支撑“继续刚才的工作”。
- `core/recovery.py`：失败自动修正与停止逻辑，可在执行结果页展示。
- `tools/quality_*` 与 `tools/execution_*`：可作为开发者调试视图入口。

维护约定：

- 单个 Python 文件原则上控制在约 400 行以内；超过 1000 行必须拆分。
- 根目录新增文件需要谨慎，优先新增到领域子包。
- 根目录门面文件必须保持很薄，只做 re-export，不承载业务逻辑。
- 新增能力时同步更新 capability 默认定义、执行 handler、UI/调试可见信息和对应测试。

## 24. 权限与隐私设计

### 24.1 权限原则

- 默认非管理员权限运行
- 所有执行动作在本地可见
- 不主动收集与当前任务无关的敏感信息
- 不上传本地文件内容，除非用户未来明确开启相关功能
- 联网能力仅限于获取经过允许的基础信息与云端模型调用
- `API Key` 视为高敏感配置，不以明文进入普通日志、提示词或调试输出

### 24.2 本地优先原则

以下数据默认本地存储：

- 任务数据
- 场景数据
- 白名单
- 操作日志
- 用户偏好

### 24.3 AI 数据边界

若调用云端模型，应尽量只发送：

- 任务标题
- 场景名称
- 抽象后的动作上下文

首阶段尽量不上传：

- 文件正文
- 敏感路径
- 隐私内容
- 桌面截图
- 明文 `API Key`

### 24.3.1 模型接入配置安全要求

首版由于采用云端模型优先，需要明确模型接入配置的安全边界。

要求如下：

- 首次使用时由用户手动输入 `API Key` 与 `Base URL`
- 保存后自动复用，无需每次重新输入
- 用户可在设置中随时替换原有配置
- `API Key` 应采用安全存储或最少加密存储
- 应用日志、错误提示、诊断信息中不得打印完整 `API Key`
- 若连通性测试失败，应提示失败原因，但不泄露完整密钥

### 24.4 联网基础信息边界

联网能力用于补充上下文，不用于扩大系统执行权限。

建议边界：

- 获取时间相关校验信息时，不覆盖本地提醒调度主逻辑
- 获取天气、节假日等信息时，应走受控接口
- 外部信息只用于提醒上下文和提示词上下文
- 外部信息不能直接触发高风险动作

## 25. MVP 范围定义

### 25.1 MVP 目标

MVP 要证明以下事情成立：

- 悬浮助手是可行且顺手的入口
- 提醒与执行分离的交互成立
- 基础动作集合已经足够好用
- 双 AI 审查 + 规则引擎 + 用户授权可建立信任
- 关键链路可以被单独调试与逐步验证
- 模块拆分后仍能稳定协作

### 25.2 MVP 必做

- 桌面悬浮助手
- 基础待办系统
- 时间提醒与稍后提醒
- 任务卡片中的建议动作展示
- `open_app / open_url / open_folder / open_file / show_tasks / restore_workspace / create_reminder / start_focus_timer`
- 用户授权三选项：`拒绝 / 本次运行 / 加入白名单`
- 白名单管理页
- 日志页
- 场景系统基础版
- 用户自定义场景 + AI 规范化
- 基础联网信息服务：时间/日期/时区/节假日/天气
- 非 `C` 盘数据目录配置
- 首次模型接入配置：`API Key + Base URL`
- 模型接入设置页：支持替换原有 `API Key + Base URL`
- 模型连通性测试与连接状态展示
- `dry_run` 模式
- `step_by_step` 模式
- 模块级模拟实现：至少覆盖 AI、执行器、联网信息服务
- 统一 `trace_id` 与调试运行记录

关于 `restore_workspace` 的 MVP 定义：

- 仅要求能根据任务或场景打开一组相关资源
- 不要求恢复窗口位置、大小和屏幕分布

### 25.3 MVP 可选

- 命令面板
- 工作区快照保存
- AI 自动补全建议动作
- 调试运行回放界面

### 25.4 MVP 不做

- 高风险动作
- 文件整理与移动
- 应用关闭
- 系统设置修改
- 任意脚本
- 对外发送型能力

## 28. 验收标准建议

MVP 可以以下列标准作为验收参考：

- 用户可以创建任务并收到桌面提醒
- 到点后不会自动打断或自动打开软件
- 用户点击“开始处理”后，可看到建议动作和授权卡片
- 授权后系统能执行低风险动作
- 加入白名单后，重复动作可在审查通过时快速执行
- 用户可查看并撤销白名单项
- 用户可查看日志，知道系统做过什么
- 用户或开发者可使用 `dry_run` 验证完整链路而不真实操作电脑
- 用户或开发者可使用 `step_by_step` 单步执行动作计划
- 在 AI 或执行器未接入真实实现时，系统仍可通过假适配器完成演示
- 任一关键流程都能通过 `trace_id` 追踪到规划、审查、规则和执行结果

## 29. 当前待确认项

以下问题尚需进一步确认，它们会影响后续原型与技术实现细节：

### 已确认 1：模型部署方式

首版采用：`云端模型优先`

具体含义：

- AI-1 规划助手与 AI-2 审查助手优先调用云端模型
- 任务、日志、白名单、场景等核心产品数据仍默认本地存储
- 规则引擎、动作执行与授权逻辑全部本地执行
- 后续再评估是否补充本地模型降级能力
- 首次使用时需要由用户配置 `API Key` 与 `Base URL`
- 配置保存后自动复用
- 用户可在后续使用过程中替换原有 `API Key` 与 `Base URL`

### 待确认 2：悬浮助手的视觉风格

目前只定义了状态和层级，尚未定义视觉语言，例如：

- 极简工具感
- 更像有存在感的个人助手
- 更像系统组件

### 已确认 3：工作区恢复的实现深度

首版 `restore_workspace` 仅做到：`打开相关软件 / 文件 / 网页`

首版不做：

- 窗口布局恢复
- 多显示器恢复
- 标签页恢复

这样处理的目的：

- 保持首版执行逻辑稳定
- 避免早期过多依赖复杂的系统窗口管理
- 把重点放在悬浮助手主链路和安全确认机制上

### 已确认 4：任务输入方式优先级

首版优先采用：`悬浮助手内创建任务`

当前约束：

- 首版主要交互尽量都在悬浮助手内完成
- 任务创建、任务提醒、建议动作查看、授权确认尽量统一在同一入口中
- 全局快捷键快速创建和自然语言创建不作为首版必须能力

### 已确认 5：场景编辑能力

首版支持：`用户自行添加和修改场景，AI 负责统一格式`

### 待办到执行的闭环

待办页现在不只负责记录任务，也承担“从任务进入工作区”的执行入口：

- 点击待办后，后端生成 `WorkspaceSuggestion`，并在详情区展示动作计划和动作级确认摘要。
- UI 提供 `拒绝`、`本次执行`、`永久确认` 三个动作级确认入口。
- `本次执行` 只执行当前工作区动作，不写入长期信任。
- `永久确认` 仅在策略要求确认且允许信任时启用，执行前写入 action-level trust。
- 执行通过 `WorkspaceExecuteWorker` 在后台线程运行，避免阻塞 Shell。
- 执行完成后，将 `trace_id`、`status`、`message` 写回待办的 `last_execution`，待办详情区展示成功、失败原因或补救建议。
- 若用户拒绝，也会写入拒绝状态，方便后续理解这个待办为什么没有继续执行。

- 用户可以手动新增动作，当前支持 `open_app`、`open_url`、`open_file`、`open_folder`、`open_project`。

- 从已加载方案进入 `确认执行` 时，仍走现有 action-level confirmation flow，不绕过策略、审查和白名单逻辑。
- `WorkspaceService` 负责 recipe 与 `WorkspaceSuggestion` 的互转，UI 不直接读取 recipe JSON 结构。

### 工作区执行反馈产品化

### 核心使用路径缩短

首页输入和预测接受应优先走“可确认方案”，而不是先进入配置型编辑页：

- 如果生成结果包含可执行动作，Shell 直接进入 `执行前确认` 页面，用户可以本次执行、永久确认或拒绝。
- 如果生成结果没有可执行动作，且用户输入属于明确打开/启动/聚焦类动作，则降级到原有对话/规划链路，让真实 planner 继续理解复杂目标。
- 如果用户从灰色预测接受了一个未完成工作区草稿，Shell 会通过 `target_id` 读取 `WorkspaceDraftStore` 里的原草稿，并直接进入确认页，不重新猜测方案。
- 如果用户接受的是具体待办预测，且该待办已有或可推断出工作区动作，Shell 会直接进入该待办的执行前确认页；没有动作时才回到待办详情。
- 通用 `工作环境选择` 页面仍然保留，用于用户需要手动微调动作、保存方案或加载已有方案的情况。

## 2026-05-02 本地状态存储架构升级：Todo / Draft / Recipe 迁往 SQLite

在可靠性补强之后，针对高频写入、潜在多进程覆盖和未来迁移成本，继续推进本地状态存储架构升级：

- `TodoStore` 默认运行路径不再使用 `runtime/data/todos.json`，而是落到 `runtime/data/desktop_assistant.db` 的 `todo_items` 表；保留传入 `.json` 路径时的兼容模式，便于测试和局部工具继续使用旧 JSON 接口。
- `WorkspaceDraftStore` 默认运行路径改为同一个 SQLite 数据库中的 `workspace_drafts` 表；继续保留 `.json` 路径兼容模式。
- `RecipeStore` 默认运行路径改为同一个 SQLite 数据库中的 `workflow_recipes` 表；继续保留 `.json` 路径兼容模式。
- `SQLiteStorage` 现在不再只维护 workflow trace / debug runs，而是增加了统一 schema migration 入口；SQLite 初始化会设置 `WAL` 和 `foreign_keys=ON`，并通过 `PRAGMA user_version` 逐步执行 migration。
- 已新增 SQLite migration：
  - `workflow_traces / debug_runs`
  - `todo_items`
  - `workspace_drafts`
  - `workflow_recipes`
- `TodoStore` 的 SQLite 模式已不再通过“全量读出 -> 修改 -> 全量覆盖”工作，而是使用按条 `SELECT / INSERT ... ON CONFLICT DO UPDATE / DELETE` 的方式，开始真正缓解多进程和高写频下的整表覆盖风险。
- `WorkspaceDraftStore` 和 `RecipeStore` 同样支持按条 upsert / delete / lookup，并可继续满足当前 Shell、工作区编辑页和 recipe picker 的调用习惯。
- 默认 SQLite 模式下，若检测到旧版 `todos.json / workspace_drafts.json / recipes.json` 仍存在且数据库表为空，会在首次访问时自动导入旧 JSON 内容，再继续走 SQLite 存储；这是一种“按需懒迁移”，避免强制一次性迁移脚本阻断日常开发。
- 旧 JSON 路径模式仍保留，主要用于单元测试、隔离测试目录和手工调试；因此当前仓库会在一段时间内同时存在 SQLite 主路径和 JSON 兼容路径。
- 这轮暂未把 `action_trust / capability catalog / app inventory / prediction / projects / activity / ui_state` 等其他本地状态统一迁往 SQLite；这些模块已经具备原子写与损坏恢复，后续可视收益继续迁移。
- SQLite migration 机制已从“仅有 `user_version` + 函数列表”的基础版，升级为带 metadata 的正式迁移机制：
  - 每个 migration 具备稳定 `version / name / description`
  - 新增 `schema_migrations` 历史表
  - 启动时不仅会执行未跑过的 migration，还会对只有 `user_version` 的旧数据库自动回填历史记录
  - 已有专项测试验证：新库迁移历史写入、旧库历史回填、主流程仍可正常读写
- 当前 migration 机制已经可追踪、可回填、可测试，但“更系统的长期演进规范”仍有后续空间，例如字段级变更手册、版本升级测试矩阵、以及更正式的迁移命名与审查约束。
- 模块命名与目录统一当前采用“聚合入口 + 兼容层 + 渐进清理”策略：

## 2026-05-04 Reminder / Todo / Tray Product Baseline

The assistant should behave like a long-running desktop companion, not a one-shot todo dialog. Current product baseline:

- Todos are split into temporary tasks and daily routine tasks. Temporary tasks can be completed, deleted, cancelled, or postponed. Daily tasks can be completed for today or skipped for today while remaining visible for future days.
- Reminder state is persisted per todo: `snoozed_until`, `last_reminder_key`, `last_reminded_at`, `reminder_repeat_count`, `daily_completed_on`, and `daily_skipped_on`.
- Reminder delivery supports due reminders, snoozed reminders, missed reminders, and limited repeat reminders. Default repeat cadence is 30 minutes, capped at 3 repeats after the original reminder.
- Quiet hours are enabled by default from local `23:00` to `07:00`. Reminder checks must use the user's local machine timezone, not UTC wall-clock time.
- Reminder delivery uses two visible channels when available: Windows system tray notification and the Mudie desktop-pet speech bubble.
- The tray menu is part of the health/debug entry point. It should expose panel restore, pet restore, health panel, app inventory refresh, and full quit.
- The app should prevent accidental duplicate background instances with a `QLockFile` lock under `runtime/desktop_assistant_ui.lock`.
- Execution trust still depends heavily on real-machine accuracy. App inventory refresh remains a first-class user-facing action because opening/focusing the right app directly determines whether users trust the assistant.
